# 原型还没上线，也能看见用户怎么用：把离线体验测试做成一个 Skill

测试一个原型，最难拿到的往往不是“好不好”的评价，而是评价背后的操作过程。

一个同事说“有点绕”，可能是找不到入口，也可能是题目看不懂。另一个人停留了很久，可能是在认真阅读，也可能已经卡住。只看完成率、最终分数，解释不了这些差异。

Offline UX Kit 要解决的就是这件事：给尚未上线的 HTML 原型增加本地行为记录，让测试者结束体验后带走一份可以直接打开的报告。开发者不需要先搭后端，也不需要测试者安装分析工具。

## 先把问题从“记录了多少点击”改成“能否还原关键过程”

埋点不是越多越好。真正有用的是几条能对应到产品决策的证据：

- 测试者有没有进入核心任务？
- 哪个步骤停留较久，期间有没有返回或改选？
- 他完成了任务，还是在某一步退出？
- 主动反馈发生在哪个节点，前面做了什么？
- 如果存在 AI 请求，等待、失败和本地降级是否影响了流程？

这些问题可以同时出现在游戏、问卷、课件、报名表和本地工具里。因此，通用层不应该叫“关卡”“大厅”或“客户”，而应该叫任务、步骤、操作和结果。具体业务由接入层解释。

例如报名表是“选主题→选形式→补充说明→提交”；客户沟通演练是“理解问题→选择回应→补充回答→结束演练”。两者内容不同，但都需要记录步骤、选择、返回和完成条件。

## 为什么同时做 Skill 和代码工具包

只提供提示词，AI 每次可能生成不同的计时方式、存储逻辑和数据格式。最容易出错的基础部分，反而被重复实现。

所以这里分成两层：

| 层级 | 负责什么 |
| --- | --- |
| Skill | 阅读现有应用，找到真正的业务转折点，列事件接入表，约束隐私与验收 |
| 通用代码 | 本地存储、事件顺序、时间切片、报告生成、导入与去重 |

AI 负责判断“哪里应该记”，代码负责稳定执行“怎么记”。这比把一个具体游戏的代码直接改名发布，更接近真正可复用的能力。

## 交付物不是一堆日志，而是一份能打开的报告

JSON 适合保留原始证据和后续合并，但不适合让每个测试者自己阅读。HTML 则可以把样式、图表和数据放在一个文件里。

首版报告提供指标卡、步骤活跃时间、问题分布、有序流程和事件明细；多人分析器可以导入多份报告，并按版本、批次和测试模式分组。Markdown 用于归档摘要，浏览器打印用于生成阅读快照。

这里有两个必须守住的口径。第一，单人报告应显示“到达或未到达”，不要用一个人的数据包装整体转化率。第二，多人数据中的“会话数”不等于“人数”：同一个人可能参加了多次测试。

不同版本、不同任务内容、纯脚本与联网 AI 模式也不能混成一个平均值。否则报告虽然漂亮，结论却可能误导修改方向。

## “停留很久”不等于“体验不好”

工具默认把最后一次有效操作后的 20 秒作为活跃计时上限。超过这段时间，页面仍然可见，但不再全部计入活跃时间。这个规则方便识别空窗，也会低估长篇阅读。

因此需要同时看可见时间、活跃时间、返回改选和主动反馈，而不是单靠停留时长给界面打分。重复点击也只能说明值得检查，不能直接证明按钮失效。

一个更可靠的处理方式是：先定位疑似节点，再回看事件顺序，结合任务内容和测试者反馈，最后决定要不要改文案、入口或流程。数据缩小排查范围，人负责解释原因。

## 本地处理也需要隐私设计

“不上服务器”不代表“什么都可以记录”。导出的 HTML 依然可能被转发，日志中也可能混入用户输入。

这版采用元数据白名单：回答只记字数，反馈只记分类，不收集密码、API Key、请求正文或业务文件内容。报告中的文字使用安全文本方式展示，嵌入 JSON 时处理可能闭合脚本标签的字符。导入报告只提取数据块，不执行对方的 HTML 脚本。

这些措施不是完整的敏感信息识别系统。接入者仍然不能把密钥塞进“选项 ID”，也不能把真实姓名当作测试代号。测试前要说明采集内容和报告接收人。

## 首版能做什么，不能做什么

目前定位是轻量离线 Web 原型测试。它不是录屏工具，不会重建每一帧界面，也不包含原生应用 SDK、后台数据平台或自动体验评分。

大厅轨迹图、自由文本反馈、旧数据转换、复杂任务漏斗和大规模会话存储都需要后续扩展。首版通过两种原创示例验证接入方式，但还不能因此推断“任意应用都能自动适配”。

刷新恢复也要分清：恢复日志，不等于恢复原应用的业务状态。中断的任务应标记中断；关闭期间的时间不能偷偷算成用户活跃。

## 如何在自己的项目落地

先选一个三到五步的核心任务，不要一开始给全站铺满埋点。

让 AI 阅读应用并给出事件表，再把通用记录器接到实际业务函数上。跑一次正常完成，再跑一次返回改选和中途退出。打开生成的报告，检查它能否解释这三种过程。

之后测试刷新、后台切换、存储不可用、重复导入和恶意输入。代码测试通过，只说明对应的逻辑符合断言；真正的浏览器文件打开、下载和存储仍要单独验收。

这一版已经完成自动逻辑测试，真实浏览器与 Windows file:// 验收仍待完成。发布时应保留这条限制，而不是沿用旧项目的测试成绩。

这个工具最值得留下的，并不是某一种图表，而是一套很小的工作习惯：每次做原型，都提前想好“用户哪里可能卡住，我需要什么证据来判断”。这样收到反馈后，才有机会从“感觉不太对”走到“下一步具体改什么”。
